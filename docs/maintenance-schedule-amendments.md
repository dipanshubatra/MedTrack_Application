# Maintenance Schedule Amendments

## Purpose

Hospitals sometimes need to change a work order after scheduling it but before a technician starts
work. Editing the task without retaining the previous plan would remove evidence needed to explain
deadline, priority, and recurrence changes. The schedule-amendment workflow applies the current
plan and stores an immutable, complete before/after snapshot in one transaction.

This is an additive Maintenance capability. Existing task creation, assignment, update, deletion,
listing, activity-history, calendar-export, and automation contracts are unchanged.

## Amendment endpoint

`PATCH /api/maintenance/{id}/schedule` requires `ROLE_HOSPITAL`. The authenticated account must be
active, have a hospital profile, and own both the task's `hospital_id` and its linked equipment.
The service obtains a pessimistic write lock on the owned task before validating or applying the
change. Concurrent amendments therefore receive distinct, ordered revision numbers and cannot
overwrite one another silently.

The request is a partial update:

```json
{
  "deadline": "2026-08-20",
  "maintenanceType": "Vendor calibration",
  "description": "Coordinate access with Radiology",
  "priority": "Critical",
  "recurrencePeriodDays": 90,
  "reason": "Vendor engineer availability changed"
}
```

`reason` is always required and is limited to 1,000 characters. The other properties are optional;
an omitted property preserves the stored value. An empty `description` clears the optional
description. A recurrence value of `0` disables completion-triggered recurrence. Recurrence cannot
be cleared to `null` through this endpoint because `null` means the field was omitted.

The server trims supplied text, canonicalizes priority to `Normal`, `High`, or `Critical`, and
rejects:

- a missing or blank reason;
- a reason longer than 1,000 characters;
- a deadline before the server's current date;
- a blank maintenance type;
- scheduling text longer than 255 characters;
- a priority outside `Normal`, `High`, or `Critical`;
- a negative recurrence period;
- a request that produces no effective scheduling change;
- a task whose status is not `Scheduled`; or
- a task whose hospital and equipment ownership keys disagree.

Successful requests return HTTP 200 with the existing `MaintenanceTask` response, with no new JSON
properties. An internal `scheduleRevision` integer starts at `0` and increments once per successful
amendment; each value is exposed as `revisionNumber` through revision history. Failed and no-op
requests do not increment it and do not write audit evidence.

Technician assignment is intentionally excluded. Hospitals continue to use
`POST /api/maintenance/{id}/assignment`, which applies its existing account-eligibility and
scheduled-state rules. Technician report fields, lifecycle status, completion evidence, ownership,
task identity, soft-delete fields, automation linkage, and SLA evidence cannot be changed by the
schedule-amendment request.

Changing a deadline immediately recomputes `slaWarningAt`, `slaBreachedAt`, and `slaState`. A task
generated by a preventive policy uses that owned policy's warning and breach windows; a manual task
uses the module defaults of three warning days and one breach day. Moving a deadline out of warning
or breach clears a stale escalation recipient. If a rule-generated deadline changes, the amended
deadline remains part of retained generated-task history and therefore becomes the cadence anchor
used by the existing automation engine for that equipment and rule.

## Revision history endpoint

`GET /api/maintenance/{id}/schedule-revisions` accepts optional `page` and `size` query parameters.
Defaults are page `0` and size `50`; size must be between `1` and `100`. Results are ordered by
revision number descending and use this page envelope:

```json
{
  "content": [
    {
      "id": 18,
      "taskId": 42,
      "revisionNumber": 2,
      "actorUserId": 7,
      "actorEmail": "hospital@example.com",
      "reason": "Vendor engineer availability changed",
      "changedFields": ["deadline", "priority"],
      "previousDeadline": "2026-08-12",
      "newDeadline": "2026-08-20",
      "previousMaintenanceType": "Inspection",
      "newMaintenanceType": "Inspection",
      "previousDescription": "Routine inspection",
      "newDescription": "Routine inspection",
      "previousPriority": "Normal",
      "newPriority": "Critical",
      "previousRecurrencePeriodDays": 30,
      "newRecurrencePeriodDays": 30,
      "amendedAt": "2026-08-03T10:30:00"
    }
  ],
  "page": 0,
  "size": 50,
  "totalElements": 1,
  "totalPages": 1,
  "first": true,
  "last": true
}
```

An active hospital account can read revision evidence for its task even after the task is archived.
The history query still joins the retained equipment row and requires both ownership paths to match.
An active technician can read revisions only for a non-archived task currently linked to their
stable user ID. Other roles are denied, and absent or cross-tenant resources use the same not-found
behavior as the existing Maintenance APIs.

## Persistence and activity timeline

Flyway migration `V11__add_maintenance_schedule_revisions.sql` is provided for H2 and MySQL. It:

- adds the non-negative `maintenance_tasks.schedule_revision` counter with a default of `0`;
- creates `maintenance_schedule_revisions` with task, hospital, and optional actor foreign keys;
- enforces one unique revision number per task;
- constrains revision numbers, recurrence values, and priority snapshots;
- indexes task timelines and hospital/time access; and
- extends the Maintenance activity-type constraint with `SCHEDULE_AMENDED`.

Each successful amendment also appends `SCHEDULE_AMENDED` to the existing general task activity
timeline. That event identifies the actor, changed field names, current assignment/status, and new
revision number. The dedicated revision table remains the authoritative evidence for exact
before/after scheduling values and the hospital-supplied reason.

Revision rows are append-only at the entity level: all mapped business columns are non-updatable,
there is no update or delete service operation, and task archival does not remove them. The task
lock, task update, revision insert, and activity insert participate in the same transaction, so a
failure rolls the entire amendment back.
